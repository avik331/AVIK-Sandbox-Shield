# Connection Interface Specification: Layer 3 Boundaries

This document defines the strict physical and virtual boundaries that contain the Layer 3 microVM, and how it interacts with the surrounding layers.

## The Tri-Boundary Architecture

Layer 3 (Kernel Isolation) sits securely within Layer 1 (Physical Air-Gap) and forms the execution boundary for the core LLM.

### 1. Connection to Layer 4 (Prompt Enforcement)
- **Topology:** The Layer 4 application firewall runs in a completely separate microVM or as a restricted process on the host.
- **Protocol:** Communication between the Layer 4 proxy and the Layer 3 LLM occurs over the virtual `tap0` interface.
- **Constraint:** The LLM does *not* listen on a public port. It only accepts connections from the specific IP assigned to the Layer 4 Proxy. All incoming payloads are structurally guaranteed by Layer 4 before traversing the virtual bridge.

### 2. Connection to Layer 5 (Guardian Monitoring)
- **Topology:** Layer 5 (the observing narrow AI) must be physically or logically unable to send data *into* Layer 3.
- **Mechanism:** Layer 5 reads the LLM's output either by:
  1. Tapping the virtual switch on the host to promiscuously read the `tap0` egress packets (pcap mode).
  2. Reading from a virtually mapped, read-only memory buffer shared by the hypervisor (zero-copy observability).
- **Constraint:** Under no circumstances does the microVM have a route back to the Guardian models.

### 3. Connection to Layer 2 (Data Diode)
- **Topology:** The microVM does not talk directly to the Data Diode.
- **Mechanism:** Egress logs (e.g., internal inference metrics) generated by the microVM are routed by the host system's `iptables` directly to the `diode0` interface. 
- **Constraint:** The microVM has no knowledge of Layer 2's existence. It blindly emits UDP logs to a designated gateway IP, which the host securely forwards out of the air-gap.

## Hardware Limitations (The "Jail")

To ensure the microVM cannot break out into the host OS, the following Firecracker constraints are mathematically enforced:

1. **No PCI/PCIe Passthrough:** The microVM cannot directly access host hardware (except heavily mediated virtual devices via virtio).
2. **SMT Disabled:** Simultaneous Multithreading is explicitly disabled to mitigate L1 data cache side-channel attacks (like MDS/L1TF).
3. **Seccomp Filters:** The hypervisor process itself is restricted by BPF filters on the host, meaning even if the microVM compromises the hypervisor, the hypervisor cannot make dangerous syscalls to the host kernel.
